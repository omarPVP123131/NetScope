# ADR-0004 · Interfaz gráfica con egui

**Estado:** propuesta · **Fecha:** Sprint 1 · **Personas afectadas:** C

## Contexto

El proyecto necesita una interfaz de escritorio que muestre tres cosas: una
lista de miles de paquetes, un árbol de campos con offsets y un volcado
hexadecimal. Las opciones razonables en Rust son `egui`, `iced`, GTK, Qt y una
base de datos con un servidor web.

## Decisión

Se usa **`egui`** (con `eframe` como envoltorio) para una interfaz de escritorio
inmediata, con estas condiciones:

1. **La lógica de la aplicación vive en un módulo independiente de `egui`.** El
   estado (qué paquete está seleccionado, qué filtro hay, dónde está el scroll)
   se puede probar sin abrir una ventana.
2. **`egui` es una dependencia solo de `netscope-desktop`.** Si mañana se quiere un
   modo terminal o una vista web, el núcleo no se toca.
3. El diseño visual es secundario: primero que funcione y que se pueda leer el
   detalle de un paquete.

## Consecuencias

**A favor**

- Dependencias puras en Rust, sin cadena de compilación de C ni de JavaScript.
- Se integra bien con un modelo basado en referencias: el *paint* recibe los
  datos ya interpretados.
- El mismo crate sirve para la interfaz y para una futura CLI, porque la lógica
  no depende de la biblioteca.

**En contra**

- Es una biblioteca más joven que GTK o Qt: hay menos ejemplos y la API cambia.
  Mitigación: se fija una versión y se encapsula en un solo módulo.
- Las tablas de miles de filas requieren virtualización explícita. Es trabajo
  del Sprint 4 de la Persona C, y está previsto.
- El tema visual por defecto no es bonito. Aceptado: la utilidad es lo primero.

## Alternativas descartadas

- **Tauri + web**: mejor aspecto, pero añade Node, un proceso web y complejidad
  de empaquetado que no aporta nada al objetivo del proyecto.
- **CLI como primera versión**: más rápida de hacer, pero el proyecto quiere una
  herramienta *visual* de campos y bytes. Se evaluará una CLI mínima en el
  Sprint 3 como complemento, no como sustituto.
